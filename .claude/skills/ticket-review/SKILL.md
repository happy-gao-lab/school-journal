# Review ticket: $ARGUMENTS

Review all code written for ticket `$ARGUMENTS` as a strict but fair senior developer. Your job is to find real problems before the ticket is closed. Don't praise, and don't summarize the code back to the user.

If no ticket ID was given, use the ticket being worked on in this conversation. If that's unclear, ask.

**This is a review, not a fix.** Don't edit any file until the user asks you to. Don't write tests. Tests are written only on explicit request, but you may point out where tests would matter most.

## 1. Load context
- Read the ticket's section in `docs/BE_TICKETS.md` / `docs/FE_TICKETS.md`, plus its block overview (Goal, Shared context), and the sections of the tickets it depends on.
- Read `CLAUDE.md` and the relevant parts of `docs/PLAN.md` (roles, domain model).
- If the Jira tools (Atlassian MCP) are available, read the SJ task too. If its description differs from the file, say so in the report. Don't fix either one.
- Backend: look at how pw-backend (`/home/dev/Documents/coding/pet/pw-backend/src`) solves the same thing (module layout, guards, db, filters). Compare against that, not against your own preferences.

## 2. Find the ticket's files
Collect the full list of files the ticket created or changed. Use every source that applies:
- `git status` + `git diff` (uncommitted, including untracked files), and `git log --oneline` / `git diff <base>...HEAD` when the work sits on a branch or in commits whose message contains the ticket ID.
- Files named in the ticket's scope (e.g. `db/schemas/users.schemas.ts`, a route under `app/admin/...`).
- Files created or edited in this conversation.
- Files the user listed in the arguments.

Also read the code around them that they depend on or that depends on them: imported services, guards, shared schemas, the module that registers a provider, the hooks a page uses, generated migrations. Bugs often sit in the joins between files.

If there is no git and the list is uncertain, show the list you found and ask the user to confirm it before reviewing.

## 3. Run the checks
Run whichever of these exist (look at the `package.json` scripts) and report any failure as a finding:
- `pnpm lint`, the typecheck (`tsc --noEmit` or `pnpm build` for the affected app), `pnpm format --check` or prettier `--check`
- Backend schema changes: check that a migration was generated by `db:generate` and matches the schema. Never run `db:migrate` or `db:push`, or anything else that touches a database.

Don't start dev servers or call external services.

## 4. Review checklist
Go through every file. Read the code itself, not just the diff hunks.

### Scope & acceptance criteria
- Check each acceptance-criteria item and mark it **met / partly met / not met / can't verify**, with evidence (file:line or command output).
- Every scope bullet must be implemented. Name anything missing.
- Name work outside the ticket's scope: features from later tickets, unrequested refactors, or BE and FE changes mixed in one ticket.
- Check for conflicts with `docs/PLAN.md` / `CLAUDE.md`.

### Correctness & edge cases
Think through the inputs and states for each endpoint, function, form and view:
- Empty, missing, `null` / `undefined`, extra unknown fields, wrong types, whitespace-only strings, very long strings, unicode, case differences (`Admin` vs `admin`, usernames and emails differing only by case).
- Boundaries: off-by-one, min/max (grade 1 and 100, 0, 101, -1, 1.5, `"50"` as a string), empty lists, a single item, large lists (pagination, limits).
- Entities that don't exist, were already processed, or belong to someone else (an IDOR: changing an id in the URL or body).
- Repeated or concurrent requests: double submit, two requests racing for the same unique resource (check-then-insert without a unique constraint or transaction), a single-use thing used twice.
- State transitions: invalid ones (approving an already rejected user, acting on a pending user), and what happens to dependent data.
- Time: expiry calculations, timezone handling for dates (a topic's date is a day, not an instant), `mode: 'string'` timestamps, comparisons done in the DB versus in JS.
- Error paths: what the user sees when the DB, the network or a token fails. No unhandled promise rejections, no swallowed errors, no leaked stack traces or internal messages.

### Domain rules (check whichever apply to this ticket)
- Only `approved` users can sign in or refresh. `pending` / `rejected` users get a clear, non-leaky error.
- Email is required for teacher and parent, optional for student. A student picks one class at registration, and only an admin can change it.
- One teacher per subject (enforced in the DB, not just in the code). Subjects are assigned to classes. Topics belong to a subject and have a date.
- Grades are integers from 1 to 100, with one per student per topic (unique constraint), saved one at a time, and **never deleted** — check that no delete route, method or cascade exists. Only the subject's teacher (or an admin) can set a grade, and only for a student in a class that has that subject.
- Invite codes are generated by the student, single-use, and expire. The code must be consumed atomically and can't be reused, used after expiry, or used by a non-parent. Check what happens if a parent links the same child twice.
- Weak/strong thresholds (< 60 / ≥ 85) and grade bounds come from `@school-journal/shared`, never as literals. Check what happens to averages with no grades.
- Visibility: admin sees everything. A teacher sees their own subjects and those classes. A student sees only their own data. A parent sees only linked children. Student-data access goes through `StudentAccessService`.

### Security
- Every non-public route has `AuthGuard`, plus `RolesGuard` with the correct `@Roles()`. Check for routes that are accidentally public.
- Authorization is checked in the service against the current user, not just the role. Don't trust ids, roles or statuses sent in the request body.
- Mass assignment: a user can't set their own `role`, `status` or `class` where they shouldn't be able to.
- Passwords are hashed (with a proper algorithm and cost) and never returned, logged or included in a response DTO. The same goes for refresh tokens and invite codes stored in the DB (they should be hashed where reasonable).
- JWT: secrets come from env, access tokens expire, refresh tokens rotate, a reused or revoked token is rejected, and logout invalidates the DB session.
- Login errors don't reveal whether a username exists. Auth endpoints are throttled.
- No SQL built from strings. Inputs are validated with zod at the boundary. CORS isn't `*`.
- FE: tokens are stored sensibly, nothing secret is in `NEXT_PUBLIC_*` variables, user content isn't rendered with `dangerouslySetInnerHTML`, and route protection isn't the only thing protecting the data.

### Data & DB
- Constraints belong in the schema (NOT NULL, unique, FKs, `onDelete` behaviour), not just in the code.
- Indexes exist for the lookups the ticket adds. Multi-step writes run in a transaction.
- No N+1 queries, no `select *` sent to the client, no unbounded queries.
- Naming: `<name>Table`, the `XTable` / `CreateX` / `UpdateX` types, snake_case columns, `timestamp(..., { mode: 'string' })`, `created_at` / `updated_at` defaults, and `updated_at` actually updated.
- Migrations are generated, not hand-edited.

### Backend conventions
- ESM with `.js` relative imports. Feature folder with `controller` / `service` / `module` / `dto.ts`. Thin controllers, with logic and access checks in services.
- Errors are Nest exceptions with messages from `constants/errors.ts`, use the correct HTTP status codes, and keep the unified error shape.
- Validation uses the zod pipe with schemas from `@school-journal/shared` (no class-validator, no duplicated schemas).
- Config comes from `constants/index.ts` / env, with no magic values. Logging goes through pino, with no `console.log` and no sensitive data in logs.
- Response shapes are consistent and don't leak internal fields.

### Frontend conventions
- Routes in `app/` are thin. Data flows `components/pages/*` → `hooks/*` → `api/*`, and pages never call axios directly.
- React Query keys come from `constants/`. Mutations invalidate or update the affected queries. There's no stale UI after a mutation.
- Forms use RHF with the zod resolver and shared schemas, through the UI kit form fields. Server errors appear in the form. Submit is disabled while pending, so a double submit is impossible.
- Every data view handles loading, empty and error states.
- UI kit components and theme tokens only — no hard-coded colors. Check light and dark mode and phone width (no horizontal scroll, usable touch targets).
- Accessibility: labels, alt text, keyboard reachability, focus after navigation or dialogs.
- Client vs server components: `'use client'` only where needed, with no hydration mismatches.
- The 401 → refresh → retry flow doesn't loop, and logout clears the cache.

### Shared package
- Enums, constants and request schemas live only in `packages/shared` and aren't duplicated in an app. Exports work from both NestJS (ESM) and Next.js.
- A schema change is reflected on both sides, or flagged as needing an FE or BE follow-up ticket.

### Quality
- TypeScript: no `any`, no unchecked `as` casts, no `!` hiding a real null, and exhaustive handling of enums.
- Dead code, leftover TODOs or debug code, commented-out blocks.
- Duplicated logic that should reuse an existing helper.
- Unclear names, oversized functions, comment density that doesn't match the surrounding code.

### Simplification & reuse (report only — never fix)
Look for code that works but could be simpler or more reusable. These go in the **Refactoring opportunities** section of the report, not in the findings, and are never applied as part of a fix.
- Functions that could be simpler: long ones that could be split, nested conditionals that could be early returns, manual loops that could be a single query or array method, redundant state or variables.
- Logic repeated within the ticket, or already existing elsewhere in the codebase, that could become a util, a shared service method, a guard/decorator, or a helper in `packages/shared`.
- FE: repeated JSX or patterns that could become a reusable component (`components/shared/` or the UI kit), or repeated query/mutation logic that could become a hook.
- BE: repeated queries or access checks that could move into a service method, repeated DB fragments, repeated error handling.
- Patterns that later tickets will clearly need again. Name those tickets.

Only suggest a refactor when it clearly pays off. Skip one-off cases where the abstraction would cost more than the duplication.

## 5. Verify before reporting
For each finding, re-read the code and confirm it's real. Check for a guard, a constraint or a validation elsewhere that already handles it. Drop anything you can't back up with a concrete scenario. Mark the ones that depend on an assumption as **Possible**.

## 6. Report
Use this format:

**Verdict:** Ready / Ready after minor fixes / Needs changes, in one sentence on why.

**Acceptance criteria:** each item → met / partly / not met / can't verify, with evidence.

**Checks:** each lint/typecheck/format/migration check → pass / fail (with the key output lines) / not available.

**Findings**, grouped by severity, most important first:
- 🔴 **Blocker:** bugs, security or access holes, data loss, a broken acceptance criterion, a domain rule violated.
- 🟠 **Major:** a missed edge case with real impact, a missing DB constraint, a convention break that will spread.
- 🟡 **Minor:** smaller convention or quality issues.
- 💬 **Nit / suggestion:** optional.

Each finding: a [file:line](path:line) link, what's wrong, a concrete failing scenario (input/state → result), and the suggested fix in a sentence or a short snippet.

**Refactoring opportunities** (informational, not fixed): each one is a [file:line](path:line) link, what could be simplified or extracted (util, shared component, hook, service method), where else it would be reused, and the payoff in one sentence. Write "None" if nothing is worth it.

**Out of scope:** things noticed that belong to other tickets. Note them, don't build them.

**Worth testing:** the 3–5 riskiest behaviours to cover if tests are requested later.

End by asking whether to fix the findings (all of them, or by severity). Refactoring opportunities aren't part of that question; they're only done if the user asks for them separately. Then wait.
